## 必须执行的研究过程

1. 使用 WebSearch 广泛搜索当前可玩的优秀网页游戏、Game Jam 作品、独立游戏原型和经典小游戏机制。
2. 至少考察 8 个作品或机制，实际打开并核对其中最有价值的来源；不要仅凭搜索摘要判断。
3. 在内部形成至少 5 个候选，并从以下维度比较：前三十秒吸引力、机制深度、重复游玩、浏览器适配、实现风险、原创转化空间。
4. 只选择综合最强的一个。可以借鉴机制设计原则，但不能直接复制名称、角色、美术、关卡或受保护 IP。
5. 参考来源至少来自 3 个有效 URL，尽量包含作品原页或开发者的一手介绍。不要捏造链接，也不要把“搜索结果页”作为来源。

不要在最终输出中暴露思维链。用简洁的“调研结论/选择理由”总结可验证的判断即可。

## 质量门槛

最终创意必须同时满足：

- 一句话就能解释核心动作与乐趣。
- 有一个鲜明的核心机制组合，而不是若干常见功能的堆砌。
- 单局约 3–10 分钟，失败后愿意立刻再来一局。
- 同时说明即时反馈、分数/成长、难度曲线和高手策略。
- 键鼠与触屏都能合理操作；若某端体验明显更好，需要坦诚说明。
- MVP 能由一个编码 Agent 在合理范围内完成，后续仍有明确的打磨空间。
- 不依赖登录、付费素材、版权角色、外部游戏 API 或长期运行的服务器。
- 与蘑菇人赛车、坦克大战以及历史 Issue 有实质差异。

## Issue 正文结构

正文使用中文 Markdown，必须依次包含：

1. `## 一句话概念`
2. `## 为什么值得做`（含调研结论和选择理由）
3. `## 核心玩法`（规则、玩家目标、失败/胜利条件）
4. `## 单局循环`（开局、中期、高潮、结算与再来一局动机）
5. `## 操作与反馈`（键鼠、触屏、视觉/音效/震动反馈）
6. `## 深度与重玩性`（计分、风险回报、难度曲线、高手策略、变化来源）
7. `## 美术与声音方向`
8. `## Codex 实现建议`（推荐技术、状态模型、关键模块、性能与移动端注意事项）
9. `## 实现范围`，分为 `### MVP`、`### 打磨项`、`### 暂不实现`
10. `## 验收标准`，使用可勾选清单，至少 8 条可测试标准
11. `## 风险与降级方案`
12. `## 参考来源`（每条含作品/文章名、有效 URL、具体借鉴点与明确不复制的内容）

Issue 正文控制在 1800–4500 个中文字符左右，避免空泛形容词。标题格式为：

`[Game Idea] 中文游戏名 — 一句机制钩子`
